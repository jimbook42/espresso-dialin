# Android privacy audit and Data Safety worksheet

Assessment as of 18 November 2026. Draft for owner review against Android v4.15.6 (5), `00ed0b6acacf9ec10602b1c99ec60b6af171bd98`. Re-audit the actual signed AAB before submitting. [Privacy policy draft](PRIVACY-POLICY.md)

## Audit evidence

| Area | Observed behavior and source |
| --- | --- |
| Local records | Dexie/IndexedDB contains beans, shots, recipes and settings, including tasting notes, photos of saved gauge views, pressure/weight/flow curves and camera calibration. Separate IndexedDB stores may contain the latest saved/imported replay and a transfer recovery journal. The Android backup build disables new development-mode replay capture. SQLite or cloud account storage is not involved. [Transfer inventory](FULL-APP-TRANSFER.md) |
| Preferences and scale | Local storage keeps preferences, local diagnostics and the last connected BLE name/address per model. Sensor use and reconnection are scoped to the relevant foreground workflows. Camera and scale permissions and remembered browser/phone device identifiers are outside full-backup migration. See `src/scales/transport/androidGatt.js`, `src/transfer/transferStore.js` and the transfer inventory. |
| Backups and exports | Full archives are unencrypted and may include original shot IDs, notes, gauge images, replay media, samples and settings. Android's document picker writes to the selected provider. Portable shot JSON can contain notes and gauge images. PNG has independent privacy toggles and SEP has sensor tracks and shot metadata when eligible. Device sharing uses a temporary attachment in private cache with a scoped read grant. The cache prunes old staged/shared files on a later export. |
| Diagnostic reports | The rolling log keeps up to 120 events or seven days, with pruning on access. Allowed app lifecycle, camera, tracking and BLE codes and JavaScript error classes appear with age. Default report includes app version, Git SHA, platform, Android version if available and limited shot-device summary counts. Model and detailed shot diagnostics require separate opt-in. User descriptions and detailed attachments can include personal information such as notes and shot IDs. Diagnostic JSON is previewed before consent. See `src/beta/problemReport.js`, `src/beta/diagnosticLog.js` and `src/beta/BetaActions.jsx`. |
| Shot contributions | Preview and consent precede sharing. The export can include measurements, provenance and timing, equipment/preparation, bean and taste context, recorded curves, recommendations and quality flags. It includes a random export ID, optional tester alias and per-row SHA-256. Private notes, raw saved IDs, exact shot timestamps, device addresses and media are excluded. An alias, fingerprints and sending email can still make a record linkable. [Contribution format](BETA-DATA.md#contribution-format-v1) |
| Automatic network and SDK evidence | The shared React UI includes `@vercel/analytics@2.0.1`. The usage preference defaults to on once settings load unless explicitly false. The page-view callback strips query/fragment. The custom event transport is disabled. Production loader code resolves to relative `/_vercel/insights/script.js` with the baseline config. The packaged Android origin is `https://localhost` with no remote server URL and the APK contains no analytics script at that path. A Chromium check serving the packaged Android assets in Android mode reproduced one local loader request (404) after setup and zero external requests observed. With the preference disabled there was no loader request. This is packaged-asset evidence, with actual WebView release network verification still pending. See `src/App.jsx`, `src/settings/anonymousUsage.js`, the packaged Capacitor config and [Vercel analytics data documentation](https://vercel.com/docs/analytics/privacy-policy). |
| Other libraries and recipients | Capacitor 8.6.2, AndroidX and the Android Shell provide local WebView, permission, export and share functionality. Capacitor Community BLE 8.3.0 communicates with the user's scale. OpenCV.js 5.0.0-release.1 and ONNX Runtime Web 1.30.0 run local processing with packaged assets. Dexie and its React hooks handle local storage, React and Lucide render UI. The release runtime dependency report had no Firebase/Play Services analytics, crash reporting, ads or billing dependency. The build has a conditional Google Services Gradle hook, so verify the final manifest and dependency report again. Gmail or another chosen destination, Microsoft's email service for the developer's Outlook address, and any selected storage provider can receive data after the user acts. There is no direct Visualizer upload integration. |

**Consent and network gate.** Camera and BLE runtime grants are separate from permission to send a file. A beta report or contribution requires a reviewed preview, explicit consent and a user-selected share or mail action. Shot-card and portable export actions explicitly select the file and recipient/provider. A share sheet opening is not proof of delivery. No automatic outbound data transfer was found in the scoped baseline check. Keep the Android analytics decision explicit: verify the signed candidate with actual WebView traffic, including startup after setup, imported/default and disabled preference states, hardware workflows and sharing. Prefer a separately approved Android-only analytics disablement if the owner wants a hard guarantee against the currently dormant loader being enabled in a future build. If analytics is enabled later, determine the types and purposes, justify consent/defaults, and update policy and declarations before release.

## Merged permission audit

Read from the signed v4.15.6 APK with `aapt dump permissions` and checked against the app and plugin manifests. API 36 target meets the current requirement for new phone apps. Recheck the final release manifest and Play device catalog, including any implied hardware filters. [Current target API policy](https://support.google.com/googleplay/android-developer/answer/11926878)

| Permission | Justification and evidence |
| --- | --- |
| `CAMERA` | Optional gauge-pressure tracking. The Android WebView accepts video capture from the local app origin only. The manifest marks camera features optional. Runtime approval is required. |
| `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT` | Android 12+ Nearby Devices for discovering a scale and connecting to read weight and use supported commands. `BLUETOOTH_SCAN` declares `neverForLocation`. The BLE library contributes `CONNECT` and marks BLE hardware optional. Check Play filtering separately because the archive also reports a legacy Bluetooth implied feature. |
| `BLUETOOTH`, `BLUETOOTH_ADMIN`, `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION` | Limited to API 30 and older in the merged manifest. Legacy Bluetooth and Android-required location access support BLE discovery. The app does not read GPS coordinates or derive a user's location. On older devices explain why the OS asks for Location before the relevant scan, then verify the actual prompt flow. |
| `INTERNET` | Normal permission inherited from the native shell template. The audited app uses locally bundled assets and has no application backend. The permission alone does not establish collection. Recheck need and actual traffic before claiming how the final build uses it. |
| App-scoped `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | AndroidX signature-level support for protecting receiver registration, without a user prompt. The FileProvider is unexported and only grants access to the specific shared file. |

The APK has no microphone, broad media/storage access, contacts, notifications, advertising ID or background location permission. File access uses the system picker or scoped share URI. Screen-awake behavior uses a window flag. Check denied camera/Nearby Devices and manual logging during physical acceptance. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions) · [Android document picker](https://developer.android.com/training/data-storage/shared/documents-files)

## Declaration worksheet

Keep this as a worksheet until actual recipient practices and the signed release are confirmed. Play treats off-device transmission as collection, including SDKs and controlled WebView code. It also treats handoff to another app as potentially shared even on the same device. A specific user-initiated transfer may qualify for the **sharing** exception when the user reasonably expects that data and recipient, or disclosure and consent meet the policy. This is a per-flow assessment. It does not remove first-party collection when we receive and retain a report or contribution. A support mailbox or pseudonymous record is not inherently anonymous or ephemeral. [Data Safety definitions and exemptions](https://support.google.com/googleplay/android-developer/answer/10787469) · [User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311)

| Flow | Candidate Play treatment |
| --- | --- |
| Shot history, calibration, camera frames, local scale data and local diagnostic log | Local processing is outside collection. BLE addresses and GPS are not part of the default outgoing report. Permission use belongs in the privacy policy. Reassess if any off-device path is added. |
| Diagnostics or support delivered to the developer | Treat as **optional collection**, provisionally covering App info and performance → Diagnostics and, as applicable, crash/error evidence. For emailed submissions also assess Personal info → Email address, and Messages → Emails or other messages and Other user-generated content for descriptions or detailed shot content. Purpose is developer communications, troubleshooting and analytics for improvement. Files retained in an inbox or review store are not ephemeral. |
| Contributions delivered to the developer | Treat as **optional collection**. Map structured shots, notes users separately add, optional tester alias and associated email metadata to the relevant Play types, provisionally Other user-generated content and Email address where applicable. Assess whether an alias is a user ID, based on how it is used. A random per-export ID is not a device ID. Brew measurements are not health measurements. Purpose is analytics and app improvement. |
| Android chooser, another app, or a cloud folder selected by the user | Review the user-initiated sharing exception for each handoff. The beta previews, affirmative consent and chosen recipient support it. Review the less detailed generic share/save exports separately, especially entire backups, PNG and shot JSON that can carry personal notes, gauge photos and replay video. Include files/documents and photos/videos if within scope of a declared flow. A selected third party operates under its own policy after receipt. |
| Developer email processor and any research storage | Confirm the provider and who can access material. Apply the service-provider sharing exception only where processing is on behalf of the developer under their instructions. Document any independent third-party access or onward transfer. No backend processor for shot logs was found. |
| Analytics | No confirmed off-device analytics collection in the Android baseline. Leave an evidence gate, then classify actual types if enabled, such as App interactions, approximate location inferred by a provider, or identifiers if applicable. Review purpose, controls, encryption and provider handling. |

- **Encryption in transit** remains unconfirmed for every collection path. The app creates plain JSON, PNG, CSV and backup documents. Do not infer a universal encrypted-in-transit claim from the HTTPS virtual WebView origin or the chooser. Confirm developer-controlled mail and storage handling.
- **Deletion and retention** need owner approval for inboxes, attachments, copies, exports, case records and any research dataset. The app has no in-app account creation. The Play in-app account-deletion rule does not apply on that basis. Still provide a working privacy contact and confirm how a user can identify a contribution for deletion. [Play account-deletion rule](https://support.google.com/googleplay/android-developer/answer/10144311#account-deletion)
- **Before declaration** confirm the publisher, privacy contact, public policy URL, owner operating practices, target audience, all active Play variants and whether additional processors are used. Verify the privacy policy matches the shipped app and completed worksheet. The public policy should be clearly titled, non-editable, publicly accessible without sign-in or geo restriction, and HTML or equivalent public text. Add a link or text inside the app and the public URL in Play Console after approval. The exclusively internal track is exempt from the Data Safety form. Closed, open and production require it.
